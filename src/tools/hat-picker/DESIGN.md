# hat-picker — Design

Author: Claude. Design lead: Jason. Source-of-truth spec. The planner turns this
into an implementation plan; the worker implements strictly against both.

## Summary

A single, self-contained `index.html` (vanilla HTML/CSS/JS, no build, no
dependencies) that lets you type entries (game suggestions) into a list and then
"pull one from the hat" at random with a fun animation. Built for family game
night — playful, quick, kid-friendly.

## Hard constraints

- **Ships as one file.** The committed `index.html` is fully self-contained — all
  HTML/CSS/JS inline, no external assets, no CDN, no npm dependencies, opens via
  `file://` or any static server. It is **build-assembled** from `source/` by the
  shared dependency-free Node build (`scripts/build-tool.mjs`, `npm run build`;
  see `docs/conventions.md` § "Build-assembled tools"). Author under `source/`
  (`index.template.html`, `styles.css`, `logic.mjs` = the pure engine, `app.mjs`
  = the DOM layer), run `npm run build`, commit the result. `npm test` runs
  `build --check` first so drift can't slip through.
- **Vanilla.** Standard browser APIs only. Inline `<script type="module">` fine.
- No third-party animation/confetti libraries — hand-rolled with Canvas/CSS.
- Current Chromium is the test target (Playwright MCP).

## Core flow

1. Type a suggestion (up to **80 characters**) into an input, press **Enter** or
   click **Add** → it joins the list.
2. Repeat to build the list of entries.
3. Click the big **"Pull from the hat! 🎩"** button → a fun animation cycles
   through the entries and lands on a **random winner**, revealed prominently
   with a celebration (confetti).
4. **Draw again** re-runs; optionally the winner is removed from the hat so the
   next draw won't repeat it.

## Layout (single column, playful, responsive)

1. **Header** — title + hat emoji, one-line tagline.
2. **Add row** — text input (`maxlength=80`) + `Add` button + a live character
   counter (e.g. `12 / 80`). Enter in the input adds. Reject empty/whitespace and
   trim. Optionally block exact duplicates (with a gentle shake, not an error).
3. **Entry list** — each row shows the entry text and a **remove (×)** button.
   Show a count (e.g. "5 in the hat"). Empty state prompts to add some.
4. **Draw area** — the big **Pull from the hat!** button (disabled until ≥ 2
   entries), a **Draw again** button (after a draw), a **"Remove winner after
   draw"** toggle, and a **Clear all** control (with a confirm).
5. **Winner reveal** — large animated result display + confetti canvas overlay.
6. **Footer** — the standardized `tools/include/footer.html` pasted verbatim
   (sentinels included) at the bottom of `<body>`, per `docs/conventions.md`'s
   "Footers" convention.

## The draw animation (make it fun)

- **Slot-machine / shuffle cycle:** on draw, rapidly cycle the reveal display
  through random entries, starting fast and **decelerating** (ease-out) over
  ~1.5–2.5s, then **landing** on the chosen winner. Use `requestAnimationFrame`
  with a time-based schedule (not fixed frame counts) so it's smooth.
- **Landing punctuation:** the winner card scales up / bounces, plus a
  **confetti burst** (hand-rolled: a full-window `<canvas>` overlay with simple
  physics — particles with position/velocity/gravity/rotation, fading out).
- Sound is out of scope (no autoplay audio). Keep it purely visual.
- Respect **`prefers-reduced-motion`**: if set, skip the cycle/confetti and just
  reveal the winner immediately.
- The button is disabled and entries are locked during an in-flight draw.

## Randomness

- Use `crypto.getRandomValues` for the actual winner selection (unbiased index
  into the entries array); the animation is cosmetic only and must not bias the
  result. The winner is chosen up front; the animation just leads to it.
- Selection is a **pure function** `pickIndex(count, rng)` (rng injectable) — the
  primary unit-test surface. Default rng wraps `crypto.getRandomValues`.

## Data & persistence

- Entries are an array of `{ id, text }`. Newest added appends to the end (or
  top — pick one; appended list reads naturally). Winner reference is separate
  UI state.
- **Entry ids: no secure-context-only APIs.** Per `docs/conventions.md`'s "No
  secure-context-only APIs" rule, entry ids are generated by a `newId()`
  helper — `crypto.getRandomValues` (available in every context) into a
  16-byte hex string, with a `Date.now()`+`Math.random()` fallback if even
  that throws — **not** `crypto.randomUUID()`. `crypto.randomUUID()` only
  exists in a secure context (HTTPS/localhost/`file://`); served over plain
  HTTP on a LAN it's `undefined` and throws, which silently broke Add. This
  exact bug hit hat-picker in production and is now covered by a regression
  test that simulates a non-secure context (see Testability).
- **Best-effort persistence:** save the entries list to `localStorage` on change
  and restore on load, wrapped in try/catch (may be unavailable under `file://`
  in some browsers — must degrade silently to in-memory). Persist entries only,
  not transient draw state.

## Removal / clear

- Per-row **×** asks for confirmation before removing that entry, via the
  shared **`confirmDialog(message)`** component (`JbcConfirm.mjs`,
  pasted verbatim into `index.html` as a classic `<script>`): `if (await
  confirmDialog('Remove this entry?')) removeEntry(id);`. **Enter = Yes** (default
  focus on confirm), **Esc = Cancel**, backdrop click cancels, focus is
  trapped while the dialog is open, and focus returns to the triggering
  control on close. Only removes the entry on explicit confirm. Per
  `docs/conventions.md` ("Destructive actions require confirmation"),
  removing a single row is a destructive action just like Clear all, so it
  gets the same treatment.
- **Clear all** asks for confirmation via the same `confirmDialog` component
  before wiping the list (`if (await confirmDialog('Remove all entries?'))
  clearAll();`); **Enter = Yes**, **Esc = Cancel**.
- `confirmDialog` is **themed** to hat-picker's look via CSS variables on `:root`
  (`--jbcc-accent: var(--brand)`, plus `--jbcc-accent-fg`, `--jbcc-bg`,
  `--jbcc-fg`, `--jbcc-radius`, `--jbcc-btn-radius`, `--jbcc-focus`,
  `--jbcc-cancel-border`), so the highlighted **"Yes"** button renders as a
  clear, filled coral primary — not the bare system-color fallback, and never
  the same as "Cancel" — per `docs/conventions.md`'s "Each adopting tool must
  set `--jbcc-accent`..." rule.
- This replaces the tool's earlier bespoke, hand-rolled `kind: 'row' | 'all'`
  confirm modal (`#clear-confirm-modal`/`openConfirm`/`closeConfirm`/
  `confirmModalAction`) — removed in favor of the shared, pasted component.
  `confirmDialog` has no `data-testid`s of its own (it's a tool-agnostic pasted
  component); tests drive it via `getByRole('dialog')` and the "Yes"/"Cancel"
  button names.
- `window.__hatPicker.removeEntry(id)` remains a **direct, non-modal** call
  (invoked here only after `confirmDialog` resolves `true`, and exposed for
  tests) — only the real × button's click goes through the confirm dialog.
- "Remove winner after draw" toggle: when on, the drawn winner is removed from
  entries right after the reveal.

## Accessibility & UX

- Winner reveal announced via an **`aria-live="polite"`** region (the final
  value, once, after landing — not every animation frame).
- All controls are real `<button>`/`<input>` with labels and visible focus.
- Character counter has an accessible label; near-limit gets a visual cue.
- Big tap targets and legible type — kids will use it. Interactive controls
  (per-row × button, Clear all, the "remove winner" toggle's tappable label
  area) hold to the **~44px** tap-target guideline from
  `docs/conventions.md`'s "Responsive & mobile" section, not just the
  headline Pull/Draw-again buttons.
- **Icon-only buttons get a hover tooltip**, per `docs/conventions.md`'s
  accessibility baseline: the per-entry remove **×** button carries `title="Remove
  entry"` alongside its per-entry `aria-label="Remove {text}"`.
- `prefers-reduced-motion` honored (see animation).
- **Submit dismisses the mobile keyboard**, per `docs/conventions.md`'s
  "Responsive & mobile": a successful `addEntry()` calls `els.input.blur()`
  (not `.focus()`) — there's no dedicated dismiss API, but the on-screen
  keyboard follows DOM focus, so blurring hides it after tapping Add on
  iOS/Android. A **rejected** add (blank/duplicate) does **not** blur — the
  input keeps focus (and shakes) so the user can immediately fix and
  resubmit.
- **Responsive & mobile:** usable down to a ~320-360px-wide viewport — no
  horizontal page overflow, the single-column layout already stacks
  naturally at that width, long/unbroken entry text wraps
  (`word-break: break-word`) instead of forcing scroll, and the confirm
  dialog fits within a narrow viewport's padding. Verified with Playwright
  mobile-viewport test coverage (see Testability).

## Testability (build these in)

To allow Playwright-MCP browser tests without breaking the single-file rule:

- Stable **`data-testid`** on: the entry input, Add button, char counter, entry
  list container, each entry row + its remove button, the Pull/Draw button, Draw
  again, remove-winner toggle, Clear all, and the winner reveal element.
- Expose a **`window.__hatPicker`** namespace: the entries state (readable),
  `addEntry(text)`, `removeEntry(id)`, `clear()`, the pure `pickIndex(count, rng)`,
  and a **deterministic draw** entry point, e.g.
  `draw({ instant: true, forceIndex })` that skips the animation and reveals the
  given/selected winner synchronously so tests can assert the outcome
  deterministically. Keep the namespace inert for normal users.
- Ensure a test can add several entries, force a winner index, and read the
  revealed winner text, plus verify disabled states (draw disabled with < 2
  entries) and the 80-char cap.

## Deliverables

- `tools/hat-picker/index.html` — the tool.
- `tools/hat-picker/README.md` — usage.
- Tests (delivered by the tester agent): pickIndex purity/unbiased-range,
  add/enforce-80-char/trim/remove/clear, draw disabled under 2 entries,
  deterministic forced draw reveals expected entry, remove-winner-after-draw,
  reduced-motion path reveals immediately, the per-entry ×-confirm via
  `confirmDialog` (open/Enter/Esc/backdrop/direct-`removeEntry`), the
  non-secure-context (`crypto.randomUUID` unavailable) regression, and a
  mobile-viewport pass (~375x667, deviceScaleFactor 2, touch) covering no
  horizontal overflow, key controls usable, add-an-entry, and a deterministic
  draw.

## Out of scope (v1)

- Weights/odds per entry, multiple winners at once, categories, sound, sharing,
  server sync. Keep it simple and fun.
